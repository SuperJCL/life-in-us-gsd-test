和 Plan 01 的“执行约束”完全相同：
- 应用文件只读；

此外，探针里手动创建的 browser context 只能访问下面三类地址，确保即使探针结论为否，也不会连到任何线上服务：
- 回环地址（127.0.0.1 或 localhost）下不会加载子资源的路径（例如 `/probe-404`）；

任何探针都不直接请求真实的外部主机，包括两个字体主机。

         2. 依次 `goto('http://probe.invalid/')` 和 `goto('https://probe.invalid/')`，两次都应当失败，错误信息包含 `ERR_PROXY_CONNECTION_FAILED`。这说明非回环主机名没有在本机解析，而是交给了死代理，并在本机被拒绝；
         3. `goto(APP_ORIGIN + '/probe-404')` 返回 404，证明死代理没有挡住应用来源；
         4. 关闭这个 context。

         `.invalid` 是 RFC 6761 保留的顶级域，任何 DNS 都解析不到，所以就算两层都失效，这条用例也不会连到任何线上服务。中文注释写明这一点。

         **第 3 条** `PROBE-2 preconnect hints to the font hosts only ever reach the proxy`（直接观察 preconnect）：
         1. 在 Node 侧用 node:net 的 `createServer` 起一个录制代理，`listen(0, '127.0.0.1')`。每个连接只读第一块数据，取第一行（形如 `CONNECT <主机>:443 HTTP/1.1`）记入数组 `seen`，然后立即 `socket.destroy()`。它不转发，也不发起任何对外连接；
         2. 用 `browser.newContext({ proxy: { server: 'http://127.0.0.1:<录制端口>', bypass: PROXY_BYPASS } })` 建 context，并在这个 context 上加一个 route：以 `APP_ORIGIN + '/'` 开头的请求 `continue`，其余全部 `abort`。字体样式表请求在 route 层就被 abort，所以到达录制代理的字体主机连接只可能来自 route 看不到的 preconnect；
         3. 从这个 context 打开页面，`goto(APP_ORIGIN + '/')`，等 `#status` 等于 STATUS_LOCAL；
         4. 在页面里执行 `new WebSocket('ws://probe.invalid/')` 作为对照。WebSocket 同样不经过 route，用来证明“route 看不到的页面流量会交给代理”；
         5. 用 `expect.poll` 等 `seen` 里同时出现两类行：一条包含 FONT_HOSTS 中任一主机名的 `CONNECT` 行，以及一条包含 `probe.invalid` 的行；
         6. 把 `seen` 的全部内容记成 annotation（type 为 `probe`）。既不属于 FONT_HOSTS、也不是 probe.invalid 的条目不算失败（它们同样只到达了本机录制代理），但要在 PROBES.md 单独列出；
         7. 关闭 context，关闭录制代理。

         这条用例说明 preconnect 和普通请求走同一条代理路径。所以在交付配置里，preconnect 只会连到 DEAD_PROXY_SERVER 并在本机失败。和第 2 条合起来，就证明应用页面不会和字体主机或其他非回环主机建立任何连接。
