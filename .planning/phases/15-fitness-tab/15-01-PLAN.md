Phase 15 的 tracer 和数据模型。先打通一条最细的端到端路径：第五个标签「健身」→ 记录区选一个力量项、记一组 → 「保存训练」经 `commit(["wo:"+date], …)` 写进 `state.workouts` → 本机保存和云端上传 → 刷新后从 `normalize` 读回 → 本周页当天出现一行「健身 · 卧推（共 1 组）」→ 点这一行回到健身页那一天。再把数据形状一次定全：`state.workouts` 的 normalize / importProblem / 导入白名单，计划里可选的 `cardio`（有氧项）和三个示例有氧项。

- Task 1（tracer）：上面的整条路径，本地版和云端版各一条用例；第五个标签、`#tab-fit` 外壳、UI-SPEC 的整段 CSS 骨架、门控属性一次放好。
- Task 2：数据模型收尾（importProblem、LEGACY_KEYS、计划的 cardio、DEFAULT_PLAN 示例有氧项、emptyPlan、planUsedIds）和纯函数单元用例；证明现有的数据、安全、导出用例不受影响。

**数据模型的决定（项目约束点名，必须在这里写明）：**
1. **形状和同步键：** `state.workouts[<YYYY-MM-DD>] = {lifts:[{id,sets:[{w,r}]}], cardio:[{id,m,d?}]}`，一天一条（D-06）。同步键 `"wo:"+date`。按 15-PATTERNS「commit 的契约」，键只是触及标记，合并靠重放 fn；fn 是 `s=>woPut(s,date,day)`：先确保 `s.workouts` 是对象，再把这一天整个换成闭包里带着的深拷贝，所以幂等、只碰这一天，两台设备在不同日子记的训练互不覆盖；同一天两边都改时以最后上传的为准（与 SYNC 现有规则一致，15-07 用例证明）。
2. **`normalize` 只在非空时输出 `workouts`（不是总输出 `workouts:{}`）。** 理由：`normalize` 的返回值是固定形状，现有用例大量做深度相等比较（`tests/e2e/io/export.spec.ts` 的 IO-03、`tests/cloud/conflict-snapshot.spec.ts:163` 的键列表、迁移脚本自检、v1 的 154 条），总是输出会让这些用例因为多一个空键而红；只在非空时输出，旧用例一行不改。代价是读 `state.workouts` 的代码一律经 `woMap(s)`（不是对象就当 `{}`），写入经 `woPut` / `woDel`，删到最后一天时连键一起去掉。`normalizePlan` 对 `cardio` 用同一规则（`tests/cloud/login.spec.ts:96` 逐字比较空计划，大量 cloud 用例 `lastPlan` 与 `syntheticPlan` 深度相等），读 `plan.cardio` 一律经 `planCardio(p)`。
3. **有氧 id：** 新前缀 `r-`，`CARDIO_ID_RE=/^r-[A-Za-z0-9_-]{1,40}$/`；示例有氧项也用前缀 id `r-run`、`r-bike`、`r-walk`（不用裸字母，免得和 `LIFT_ID_RE` 的裸字母 id 同形，D-02）。`stable-ids` 冻结这三个 id（Task 2 的单元用例）。
4. **旧页面丢键的风险（15-CONTEXT Integration Points）：** 已上线的 Phase 14 版本加载新数据时 `normalize` / `normalizePlan` 会丢掉 `workouts`、`cardio`，随后保存就会冲掉它们。**决定：不在新版本里做"保留未知键"。** 理由：保留未知键救不了已经部署的旧页面（风险来自旧代码，不是新代码），反而削弱 SEC-01 的白名单（导入和载入只留认识的键）；而本阶段只在本机开发，线上只有测试账号，真实数据要等 Phase 16 新版本上线、所有打开的页面都点过「有新版本」更新之后才迁移。这一条写进 threat_model（accept）和 SUMMARY，交给 Phase 16 的上线步骤：先确认所有设备都已换成新版本，再记第一条训练、再迁移真实数据。

**规模：** 估算 130000（无校准样本，factor 1，置信度 low），超过 100000 的建议线。只拆成 2 个任务：tracer 必须一次穿过数据、写入、同步、渲染、其他视图五层；数据模型的其余部分都是纯函数段里的改动，和单元用例一起放在 Task 2。
