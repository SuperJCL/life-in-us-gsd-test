# Phase 15: 健身页（Fitness Tab） - Context

**Gathered:** 2026-11-13
**Status:** Ready for planning（界面是新标签页，规划前先做 UI 设计契约 `/gsd-ui-phase 15`）

<domain>
## Phase Boundary

新增第五个标签「健身」，把健身从「目标」页和文字记录里独立出来。这一页负责四件事：
- 记录当天的力量训练（一组一组记重量 × 次数）和有氧（时长，距离可选）；
- 显示力量目标和本周训练次数；
- 显示每个力量动作的趋势图和每周有氧总时长；
- 列出训练历史。

训练数据按账号存进现有的 state 文档，离线可记、跨设备同步，导出导入不丢。记过训练的日子在本周、日历、时间线里显示为一行「健身」，计入本周训练天数。

对应需求：FIT-01 到 FIT-05。所有者在讨论中加了两项，需求和路线图的措辞随本文件一起改，见 D-14：
- 有氧（时长、距离）也进健身页；
- 力量项上限从 8 个放宽到 20 个。

本阶段不改这些：
- 5 个固定类别；
- 「记一笔」的健身文字记录（照样能记，照样算训练日）；
- 服务器的数据结构（不新增文档类型）；
- 目标组和任务。

</domain>

<decisions>
## Implementation Decisions

### 能记哪些训练（所有者讨论决定）
- **D-01:** 力量训练只能从计划里的力量项选。一次训练里，每个动作一组一组记「重量 × 次数」。自重动作（引体、俯卧撑）也统一记重量 × 次数，徒手填 0，附加配重时填配重。
- **D-02:** 有氧也在健身页记。
  - 有氧项和力量项一样在编辑计划页增删改：名称、备注，可以选填一个目标，比如每次 5 公里。示例计划带几个常见项，比如跑步、骑行、快走。
  - 每次有氧时长必填、距离可选，没有距离的项目（跳绳、椭圆机）也能记。
  - 有氧项的 id 用新的前缀，不和 `P`、`g-`、`t-`、`l-`、`c-` 撞。
- **D-03:** 训练时只能选计划里已有的动作。健身页上提供「去编辑计划添加动作」的入口，不在健身页当场新建动作：计划要联网才能保存，训练记录断网也要能记，两者冲突。
- **D-04:** 力量项上限从 8 个放宽到 20 个，即 `PLAN_MAX.lifts`，改的是 12 D-17 的一个数。有氧项的上限由 Claude 定，同为 20 个。— **Reversibility:** reversible — 只是校验上限，已有计划不受影响。

### 在本周、日历、时间线里怎么显示（所有者讨论决定）
- **D-05:** 训练不生成文字记录。本周、日历和时间线直接按训练数据显示一行，例如「健身 · 卧推、深蹲（共 7 组）· 跑步 30 分钟」。点这一行打开健身页的这次训练。数据只存一份，改了训练，这一行跟着变。
- **D-06:** 一天只有一次训练。同一天再记，就并进当天那次，比如早上练力量、晚上跑步。
- **D-07:** 本周页的「训练 N 天，目标 a～b 天」把两种日子都算作训练日：记了训练的日子，以及有「健身」类文字记录的日子。同一天只算一次。以前只写了文字的日子照样算，历史数字不变。

### 趋势图（所有者讨论决定）
- **D-08:** 力量动作每个一张折线图，指标可在三者之间切换，默认**最大重量**：
  - 最大重量：当天最重的一组；
  - 估算单次最大：Epley 公式，重量 ×（1 + 次数 ÷ 30）；
  - 总训练量：所有组的重量 × 次数之和。

  在「最大重量」和「估算单次最大」下，画一条编辑计划里目标重量的**虚线**。
- **D-09:** 某个动作的所有组重量都是 0 时（徒手），这个动作的图自动改看「单组最多次数」和「总次数」。
- **D-10:** 图按组翻页：电脑上一次 **4 张**（两行两列），手机上一次 **3 张**（上下排）。用「上一组 / 下一组」翻页，并显示当前是第几组。动作顺序跟编辑计划里一致。指标和时间范围对当前这一组里的图一起生效。
- **D-11:** 时间范围：最近 1 个月、3 个月、半年、1 年、全部。默认**最近 1 个月**。所有者改掉了路线图原来写的 4 周 / 3 个月 / 全部。
- **D-12:** 有氧只看**每周有氧总时长**，一张按周的柱形图，不分项目，时间范围和 D-11 共用。

### 健身页放什么（所有者讨论决定）
- **D-13:** 页面从上到下依次是：
  1. 今天的训练（记录区）；
  2. 本周训练次数和力量目标（每个力量项的当前值、目标、进度）；
  3. 趋势图；
  4. 训练历史。

  健身说明 `fitNote` 是一个可展开、收起的「说明」按钮，第一次打开时默认展开（14 D-03）。
- **D-15:** 力量项的「当前值」**完全由训练记录算**：取最近一次训练里最重的一组。没记过训练时，用以前手填的值（`state.lifts[id].cur`）。不再有手填框，目标页上 `saveLift` 那套输入去掉。

### 需求和路线图的措辞
- **D-14:** 下面这些按 D-02、D-04、D-08 到 D-12 改写，随本文件一起提交：
  - REQUIREMENTS 的 FIT-01、FIT-02、FIT-03；
  - 路线图 Phase 15 的成功标准 1 到 3；
  - 新增有氧、20 个上限、5 档时间范围和默认 1 个月、电脑 4 张 / 手机 3 张、每周有氧总时长。

### Claude's Discretion（技术判断，已在讨论开头告诉所有者）
- **训练数据存在现有的 state 文档里**，不新建文档类型。原因是服务器 `journey_docs.kind` 是只有 `state`/`plan` 两个值的 select（`pb/pb_migrations/1794096100_journey_docs.js:19`），新增类型要做服务器迁移。按每周 3 次估算，一年大约几十 KB，远在 4 MB 上限内。
- **以前手填的力量历史**（`state.lifts[id].hist`，每个动作最多 30 个点、每天一个值）作为「最大重量」画进趋势图。因为没有次数，不参与另外两个指标；训练历史里也不列这些点。
- 记录区的具体交互：
  - 打开某个动作时，带出它上次训练的各组作参考或预填；
  - 「复制上一组」；
  - 删除一组；
  - 修改、删除整次训练，删除可以撤销（路线图成功标准 2）。

  具体做法由 UI 设计契约定。
- 趋势图选的时间范围按设备记住，存在 `localStorage`，只当作个人偏好。
- 编辑计划页的示例挑选（Phase 14 的 `dialog#sample`）里，要不要加「有氧项」一栏：倾向于加，和力量项一样逐个挑。
- 日历 CSV 导出里要不要给训练日一行：倾向于加，写成「健身 · …」的摘要。
- 有氧项目标的显示位置和样式。
- 本周没有每周有氧总时长目标，以后需要再加。

</decisions>

## Existing Code Insights

### Reusable Assets
- `lift(id)`（`us-journey-tracker.html:712` 附近）读 `state.lifts[id]`，得到 `{cur,hist}`。
- `saveLift`（2389 行附近）把每天一个值追加进 `hist`，只保留最后 30 条，经 `commit(["lift:"+id], …)` 写入。本阶段去掉手填，`state.lifts` 只作为历史来源，只读。
- `commit(keys, fn)`（935 行附近）：按条目键做合并和同步的写入口。训练记录用按日期的键，例如 `wo:<日期>`，这样两台设备在不同日子记的训练互不覆盖。
- `eventsOn(date)`（2106 行附近）返回当天的 `{logs,due,done}`。训练行要从这里或旁边的同类函数接进本周、日历日面板和时间线。
- 本周页的健身目标行（`renderWeek` 内，`C.n==="健身"` 那段，2116 行附近）现在只数 `cat==="健身"` 的记录日。按 D-07 改为记录日和训练日的并集。
- `PLAN_MAX`（858 行）里 `lifts:8` 改成 20（D-04），有氧项要新增同类上限。
- 标签栏：`<nav class="tabs" role="tablist">`（485 行），现有 `data-tab` 为 `wk`、`cal`、`goal`、`tl`。新增 `fit`；375 px 下 5 个标签要放得下。
- `renderGoals` 里的健身卡片（`fit` 变量、`.lifts`、`data-lift`、`data-liftsave`）整块搬到健身页并改成只读加训练数据；目标页只剩目标组和已归档区。
- `goalsBars()` 的 `data-w` 加 CSSOM 写法，是严格 CSP 下画宽度的现成办法。趋势图用 SVG，坐标写成属性，不写 `style=""`。

### Established Patterns
- 整页字符串模板渲染加事件委托（`data-*`），用户文字一律经过 `esc()`。
- 数据写入走 `commit`，离线先存本机、联网后上传（Phase 10）；计划写入只在联网时能保存（12 D-11）。
- 导入经 `normalize` 白名单（738 行 `normalize(s)`、`LEGACY_KEYS`），新键 `workouts` 要加进白名单和校验，恶意文字和非法数值要挡住（SEC-01）。
- 每次改应用都要重新记录 `APP_SHA256`。测试从 `tests/support/strings.ts` 读文案。

### Integration Points
- **计划的数据形状要加 `cardio`（有氧项）**，`normalizePlan`、编辑计划页、示例计划和导入识别都要跟着改。
- **state 要加 `workouts`**，`normalize`、导出（JSON 和日历 CSV）和迁移脚本都要跟着改。
- **风险（上线顺序）：** 旧版本的页面加载新数据时，`normalize` / `normalizePlan` 会丢掉不认识的键；如果旧页面随后保存，可能把 `workouts` 或 `cardio` 冲掉。本阶段只在本机开发；新版本在 Phase 16 部署时，线上只有测试账号，真实数据在新版本上线后才迁移。规划时要确认这一点，并决定要不要加防护，比如保留未知键。
- 本周、日历和时间线的「健身」筛选要把训练行算进去（时间线有按类别的筛选）。

## Specific Ideas

- 所有者最初的说法是：「健身的记录我想独立出来，因为这是一大块，包含健身目标的记录、健身当天做组的数据记录、按做组记录的趋势图生成」。所以重点是做组记录和趋势图。
- 所有者在讨论中主动加了有氧，但只要「每周有氧总时长」这一张图，不要分项目的配速或距离图。
- 图要能多看几张：手机上 2 张嫌少，定为 3 张。

</specifics>
