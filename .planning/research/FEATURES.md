# Feature Research

**Domain:** 3 人私用的个人记录应用，加账号登录、服务器存储、实时同步、离线优先、个人计划编辑（里程碑 v2.0 多账号云端版）
**Researched:** 2026-11-05
**Confidence:** MEDIUM（PocketBase 官方文档给出的行为是 HIGH；离线优先、冲突处理、iOS 主屏幕应用的行为是行业惯例加推理，MEDIUM；标 LOW 的条目需要在对应阶段当场验证）

> 范围：只覆盖 v2.0 的新增能力。四个视图、记一笔、编辑弹窗、撤销 toast、导出导入这些现有功能不重复研究，只在“依赖现有代码”一节说明它们要怎么改。
> 隐私：本文只描述结构，不含任何个人计划文字、路径或邮箱。示例计划只给结构规格，文字由实现阶段写通用占位文案。

## 先给结论（供 REQUIREMENTS.md 取用）

1. **稳定 id 方案：不需要迁移 task id。** 把现有的 `P<n>` 和 `P<n>-<i>` 原样冻结成“不透明字符串 id”，写进车主账号的种子计划；以后新增的目标组和任务用 `g-<uid>`、`t-<uid>`。id 永远不再由位置推算，显示用的 “P1…Pn” 标签改为按顺序在渲染时生成。已有的 `state.tasks`、`state.custom[].group` 一个字节都不用改。
2. **删除有进度的任务用“归档”，不用硬删。** 否则时间线和日历里的“完成的计划”会凭空消失。
3. **导入必须先修 N3。** 只接受“像备份”的文件：识别新格式包装和旧版裸 state，其余一律拒绝，`{}` 不再清空数据。这是 v1.0 里登记的已知 bug，v2.0 要修，对应的 `test.fail` 用例要翻成正常断言。
4. **离线优先的三个硬前提**，缺一个就会丢数据：
   - 第一次对账成功之前不上传（避免用空默认 state 覆盖服务器）；
   - 保存失败必须重试（现在的 `flush` 在保存前就把 `dirty` 清掉，失败后不重试）；
   - 远端更新到达时不能毁掉输入框草稿（现在 `renderAll()` 会重建全部 DOM）。
5. **最后写入为准下真正会丢的是“两台设备各自离线新增记录”**（整份 state 被后上传的一方整体替换）。车主已决定采用 LWW，本研究建议加两层便宜的保护：覆盖前检测并给出明确提示；把被覆盖的服务器版本在本机留一份可下载。按 id 合并 logs 作为后续差异化功能，现在设计 schema 时不要堵死它。

## Feature Landscape

### 1. 登录与会话（Login / Session）

3 个人用的私有应用，期望是“登录一次，几乎不再看到登录页；忘了密码找管理员”。

| 行为 | 期望表现 | 说明 |
|------|----------|------|
| 登录页 | 账号 + 密码两个输入框，一个“登录”按钮，Enter 提交；密码框有“显示/隐藏”；`autocomplete="username"` 和 `current-password`，让手机和浏览器的密码管理器能填 | 沿用现有 CSS 变量和深色主题，不引入新样式体系 |
| 登录失败反馈 | 统一文案“账号或密码不对”，不区分账号不存在还是密码错；按钮在请求期间禁用并显示“登录中…”；网络不通显示“连不上服务器，请检查网络”；被限流显示“尝试太多次，请稍后再试” | PocketBase 的认证失败对两种情况返回相同错误；限流用 PocketBase 自带的速率限制（需在后台开启，LOW，实现阶段核对文档） |
| 页面启动 | 本地有未过期 token 时，**立即**用本机缓存渲染应用，后台再 `authRefresh`；没有 token 才显示登录页，且不能先闪一下应用或登录页 | 客户端 token 持久化由 PocketBase JS SDK 的 `authStore` 负责（默认存 localStorage，MEDIUM）；`authRefresh` 用来滑动延长登录期 |
| 刷新后保持登录 | 刷新、关掉标签页再开、重启浏览器都不用重新登录 | token 有效期在 PocketBase 的 users 集合里可配，建议设长（几十天），每次启动 `authRefresh` 续期（MEDIUM，默认值文档页没写） |
| 登录过期 | 管理员改了密码后旧 token 失效。设备下次联网请求遇到 401 时回到登录页，**但本机未上传的修改必须保留**，同一账号重新登录后继续上传 | 这是最容易做错的一点：401 不能触发“清空本地” |
| 登出 | 页头（或设置入口）有“退出登录”。退出时尝试先上传；上传失败则提示“有 N 项修改尚未上传，退出将丢弃”并要求确认；确认后清掉该账号的本机缓存、取消实时订阅、回登录页 | 共用电脑的隐私要求。本机缓存的 key 要带用户 id，避免 A 退出后 B 看到 A 的缓存 |
| 密码修改与重置 | **只有管理员在 PocketBase 后台做**。应用里没有“忘记密码”链接，只有一行文字“忘记密码请联系管理员” | 没有 SMTP 就不能发重置邮件，3 个人也不值得配 |
| 离线时登录 | 不支持，提示“首次登录需要联网”。已登录的设备离线照常使用 | |
| 账号隔离 | 集合规则让每个账号只能读写自己的记录，创建权限只给管理员；实时订阅同样按规则过滤 | 官方文档：订阅按集合的 ListRule/ViewRule 过滤（HIGH）。**这条需要一个真实 PocketBase 的冒烟用例（两个合成账号互相读不到）**，模拟后端证明不了隔离 |
| 手机“添加到主屏幕” | 提供 `manifest`（`display: standalone`、图标、主题色）、`apple-touch-icon`、`theme-color`；添加后全屏打开、没有浏览器地址栏 | 需要 HTTPS 域名；iOS 上主屏幕应用的存储与 Safari 是分开的，第一次要重新登录一次（MEDIUM） |
| 应用壳离线可打开 | 用 service worker 缓存页面本体和 SDK，断网时也能打开应用 | 没有它，“离线优先”在刷新页面后就失效；单文件页面的缓存版本更新策略要想清楚（见 PITFALLS） |
| iOS 存储回收 | Safari 里 7 天不访问会清掉站点的脚本可写存储；添加到主屏幕的应用单独计时，通常不受影响（MEDIUM，来源较旧） | 服务器是唯一的真相；本机缓存丢了可以重新拉。长期离线且有未上传修改的设备风险最大，状态栏要持续提示 |

### 2. 编辑计划页（Plan Editor）

#### 2.1 计划的数据形状（结构，不含文字）

每个账号一份计划，与记录分开存放、分开同步（改计划不应该和记一笔互相覆盖）：

```
plan = {
  groups: [ { id, cat, name, note?, tasks: [ { id, text, archived? } ], archived? } ],  // 数组顺序即显示顺序
  lifts:  [ { id, n, unit, target, def, note?, archived? } ],
  fitGoal: [min, max],                       // 本周健身次数目标
  presets: { [categoryName]: string[] }      // 内置预设基础列表
}
```

- `cat` 只能取现有 5 个类别之一；**类别本身不可编辑**（`logs[].cat` 存的是中文显示名，改类别会让历史记录失配）。
- 不再有 `GROUPS`、`BUILTIN`、`GCAT`、`LIFTS`、`FIT_GOAL` 这些写死的常量；它们变成从计划推导。

#### 2.2 稳定 id 方案与迁移（推荐）

| 项目 | 方案 |
|------|------|
| id 形式 | 不透明字符串，必须匹配 `^[A-Za-z0-9_-]{1,40}$`；永远不由位置、文字或内容推算 |
| 现有内置任务 | **原样冻结**：目标组 id 就是 `P1`…`P7`，任务 id 就是 `P<n>-<i>`。车主账号的种子计划用这些 id，所以 `state.tasks`、`state.custom[].group` 和旧备份里的进度**无需任何转换** |
| 新增项 | `g-<uid>`（目标组）、`t-<uid>`（任务），`uid()` 沿用现有函数；力量项沿用现有 id（如已有的 `bench` 一类），新增的用 `l-<uid>` |
| 显示标签 | “P1…Pn” 改成渲染时按目标组当前顺序生成，不再等于 id。拖动排序后标签跟着变，这符合“按优先级排序”的含义；CSV 导出里的组名也用同一个函数 |
| 自定义待办 | `c-<uid>` 保留，仍放 `state.custom`（它是用户在目标页即点即加的记录，不属于计划）。`custom[].group` 引用目标组 id |
| 判断是否自定义 | 把 `/^P\d-\d+$/`（app 文件约 522 行）换成“查计划里有没有这个 id” |
| 示例计划 | 用**固定 id**（如 `ex-g1`、`ex-g1-t1`）。两台新设备同时首次登录都会写入示例计划，因为 id 相同，后写的覆盖先写的结果一致，不会出现重复 |
| 车主迁移 | 种子计划由本地脚本从现有 app 文件的内置计划**生成一份不进 git 的 JSON**（文件名加入 `.gitignore`，隐私钩子会拦截个人文字），再用“导入”页导入到车主账号。所以导入功能必须能单独导入计划 |
| 旧备份导入到没有对应计划的账号 | 进度 key 对不上计划里的 id。**不要删除这些进度**，保留在 `state.tasks` 里；导入摘要里提示“有 N 项任务进度在当前计划里找不到对应项” |

被否决的方案：
- 内容哈希 id：改任务文字就变 id，进度丢失。
- 保留位置 id 加“编辑时重映射表”：多设备并发编辑时重映射会互相冲突，而且就是现在的 bug 换了个名字。

#### 2.3 期望的操作与安全护栏

| 操作 | 期望行为 | 护栏 |
|------|----------|------|
| 目标组：新增、改名、改类别、改备注 | 即时在草稿里生效 | 名称必填；类别只能从 5 个里选 |
| 目标组：排序 | 每行“上移/下移”按钮（手机上可靠）；拖拽是差异化功能 | 只改数组顺序，id 不动 |
| 目标组：删除 | 该组下没有任何任务有进度、也没有自定义待办 → 直接删，给撤销 toast。有进度或有自定义待办 → 弹确认，写明“N 项已完成、M 项设了截止日期、K 个自定义待办；历史记录会保留在时间线，目标页不再显示” → 确认后**归档**而不是物理删除 | 归档项放在编辑页底部“已移除”折叠区，可恢复 |
| 任务：新增、改文字 | 改文字不影响进度（id 稳定）。已完成任务在时间线显示新文字，这是可接受的，写进说明即可 | 文字必填，长度上限；允许重名但给出提示 |
| 任务：删除 | 同上：没进度直接删（可撤销），有进度归档并提示 | |
| 任务：排序、移到别的组 | 组内上移下移是必须的；跨组移动是差异化功能。因为 id 不变，进度跟着任务走 | |
| 力量项：新增、改（名称、单位、目标、默认起始值、备注）、排序 | `target` 必须是正数，`def` 是非负数，`unit` 必填 | |
| 力量项：删除 | 同样归档：历史记录 `state.lifts[id].hist` 保留，不显示在目标页 | |
| 每周健身目标 | 两个整数，最小值 ≤ 最大值 | |
| 预设标签（基础列表） | 按类别增、改、删、排序 | 见 2.4 的设计取舍 |
| 保存方式 | **草稿加“保存/取消”**，不要边输入边同步。原因：实时同步会把“正在编辑一半”的计划推给其他设备，id 重排也会造成界面抖动 | 有未保存修改时离开页面（返回键、切换标签）要确认 |
| 撤销 | 删除类操作沿用现有的 5 秒撤销 toast；“取消”丢弃整个草稿 | |
| 规模上限 | 目标组 ≤ 20，每组任务 ≤ 50，力量项 ≤ 8，文字长度有上限（名称约 40，任务约 200） | 防止计划和同步文档无限变大 |
| 空计划 | 允许删光。目标页和本周页要能渲染“0 个目标组、0 个力量项”的空状态 | 现有渲染代码没有这个状态，要核对 |
| 所有计划文字 | 渲染前必须 `esc()`；id 渲染进 `data-*` 前必须通过 id 正则 | 计划现在来自服务器和导入文件，不再是受信常量（CONCERNS 里的 XSS 项因此变成必须修） |
| 入口 | 目标页里加“编辑计划”按钮，URL hash（如 `#plan`）路由，返回键可用。**不新增第五个标签** | 符合“只加登录页和编辑计划页” |
| “恢复默认计划”按钮 | **不做**（见反特性）。只在计划为空时提供“载入示例计划” | |

#### 2.4 新账号默认值与预设标签的取舍

- **新账号默认给一份示例计划**：约 2 个目标组、每组 3 个任务、2 个力量项、每类别少量预设，文字用通用占位。页面顶部一条提示“这是示例计划，可以随意修改”。示例计划由客户端在发现该账号没有计划时写入，用固定 id 保证幂等。相比空白，示例能直接让目标页、本周页有内容可看，也示范了各字段怎么填。
- **预设标签两层设计（待车主在 REQUIREMENTS 阶段确认）**：现在 `state.presets[cat] = {add, hide}` 是在内置预设之上的“增量”，由记一笔里的现有 UI 维护。
  - 推荐 v2.0 **保持增量不动**，计划里的 `presets` 只是基础列表，编辑计划页只改基础列表。这样 composer 的代码和测试一行不改。
  - 缺点：预设有两处可编辑，需要在编辑页写一句“这里改的是基础标签，记一笔里加的标签不受影响”。
  - 备选：迁移时把 `add/hide` 折叠进计划基础列表，composer 直接改计划。更干净，但要改 composer 并且改 v1.0 的预设用例。

### 3. 实时同步的用户体验（Realtime Sync UX）

| 场景 | 期望表现 | 说明 |
|------|----------|------|
| 另一台设备改了数据 | 当前页面静默更新，状态栏短暂显示“已同步另一台设备的修改”（约 3 秒），**没有弹窗、没有确认** | 不要做“有更新，点此刷新”那种打断式提示，3 个人自用不需要 |
| 自己的写入回流 | 订阅会把自己刚写的更新也推回来，必须识别并忽略（比较版本号或本机生成的写入标记），否则会闪烁甚至循环 | |
| 正在输入时收到远端更新 | 不能清掉记一笔的草稿、焦点和周复盘输入框。现有 `renderAll()` 会重建全部 DOM（ARCHITECTURE 已记为反模式），所以应用远端更新前要保存并恢复：composer 草稿、周复盘 textarea 的内容和光标、当前标签和选中的日期 | 周复盘有 800 毫秒防抖，输入中收到远端的同一周复盘更新时，本机输入优先 |
| 编辑弹窗打开时目标记录被远端改了或删了 | 弹窗保持打开；保存时如果该 id 已不存在，提示“这条记录已在其他设备被删除” | 现有 `openEditor` 用 id 查找，找不到会直接返回，要补保存时的检查 |
| 重连 | 官方文档：SSE 在 5 分钟没有消息后服务端会断开，客户端会自动重连；文档**没有说**断线期间错过的事件会不会补发（HIGH：这个沉默本身；补发与否按“不补发”设计）。所以每次 `PB_CONNECT`（含重连）都要**整份重新拉取**并对账；页面从后台回到前台（`visibilitychange`）也重新拉一次，因为手机会挂起 SSE | |
| 状态指示 | 沿用页面底部现有状态栏，状态集合：**已同步**、**保存中…**、**离线，N 项修改待上传**、**同步失败，稍后自动重试**、**登录已过期，请重新登录**。只有服务器确认后才显示“已同步”，不能乐观显示 | 现有 `setStatus(store.label)` 在保存成功后显示固定标签，要换成这套状态机 |
| 冲突提示（LWW） | 用平实的话：“这台设备离线时的修改已上传，覆盖了其他设备较早的修改。” 不弹字段级合并对话框 | 见第 4 节的保护措施 |
| 谁在线、正在编辑 | 不做 | 反特性 |

### 4. 离线优先（Offline-first）

**机制：** 整份 state 的 LWW 下不需要操作日志。本机保存“完整快照 + 脏标记 + 上次同步到的服务器版本号”，联网后上传一次快照即可（多次修改自然合并成一次上传）。

| 期望 | 具体要求 |
|------|----------|
| 先存本机 | 每次 `persist()` 同步写本机缓存（key 带用户 id）。本机写入是同步的，所以 `pagehide` 时不会丢；网络上传则可能来不及完成 |
| 脏标记要落盘 | `dirty` 和“基线版本号”存进本机缓存。关页面后再打开，如果还是脏的，启动时就继续上传 |
| 失败要重试 | **修掉现有 bug**：`flush` 现在在 `await save` 之前就清了 `dirty`。改成成功后才清；失败时指数退避重试（如 2、4、8…最大 60 秒），并且在 `online` 事件、`visibilitychange` 回到前台、SSE 重连时立即重试一次 |
| 判断是否在线 | `navigator.onLine` 不可靠（连着 Wi-Fi 但不通外网时仍为 true）。以请求是否成功为准；中国到香港的链路偶尔不稳，所以“网络请求失败”是常态要处理的情况，不是例外 |
| 启动顺序 | 先用本机缓存立即渲染，再后台对账。**第一次对账成功之前不上传**，并且“请求失败”不能被当成“服务器上是空的”。这同时修掉“加载未完成时的修改被覆盖”的已知 bug |
| 重连后的对账 | 拉取服务器当前版本 → 如果本机没有未上传修改，直接采用服务器版本；如果本机有未上传修改且服务器版本等于基线，上传；如果本机有未上传修改**并且**服务器版本已变（真冲突），按车主决定“后上传的为准”，上传本机，同时把被覆盖的服务器版本在本机留一份并提示 |
| LWW 下会丢什么 | ① 两台设备在同一时间段各自新增记录，后上传的一方整份替换，另一方的新增记录消失；② 一台设备删掉的记录会被另一台旧设备的上传“复活”；③ 旧设备上传会覆盖较新的计划修改；④ 同一字段同时改，后者胜（可以接受） |
| 保护措施（推荐） | **P1：** 冲突检测加明确提示，不让覆盖悄悄发生。**P2：** 被覆盖的服务器版本在本机留一份（只留最近一次），设置里提供“下载冲突前的版本”（与导出同格式，可直接再导入）。**后续：** 对 logs 在冲突时按 id 取并集（logs 已有稳定的 `uid()`），再加一个小的“已删除 id”列表防止复活；现在不做，但同步粒度（整份文档 or 每条记录一个文件）的架构决策不要堵死这条路 |
| 3 个人的实际风险 | 每人通常一部手机加一台电脑，真冲突很少。最主要的现实风险不是并发，而是**长期离线的旧设备突然上传**；状态栏一直显示“N 项待上传”可以降低这个风险 |
| 后台同步 API | 不依赖。iOS 不支持 Background Sync，只靠 `online`、`visibilitychange`、SSE 重连这几个事件 |
| 多标签页 | 同一浏览器开两个标签页会共用本机缓存。依赖实时订阅互相同步即可；跨标签页的登出传播（`storage` 事件）是低优先级的锦上添花 |

### 5. 按账号导出与导入（Export / Import）

#### 5.1 格式兼容

- **旧备份**：`JSON.stringify(state)` 的裸对象（字段 `arrival, tasks, custom, logs, lifts, reviews, presets`），没有计划、没有版本号。
- **新备份（推荐）**：外面加一层包装，里面放旧 state 字段和计划，例如 `{ app: "us-journey-tracker", format: 2, exportedAt, plan, state }`（具体字段名由实现阶段定，关键是有 `format` 标识）。
- **导入时的识别规则**：
  1. 有 `format: 2` 包装 → 按新格式；
  2. 否则如果是对象，并且 `logs/tasks/custom/lifts/reviews/presets/arrival` 里至少有一个且类型正确 → 当作旧备份，只含记录；
  3. 其余（`{}`、数组、字符串、字段全不认识、空对象）→ **拒绝**，toast“这不是备份文件”，不弹确认框，数据不变。
- 这条直接修复 N3（`{}` 清空数据）。v1.0 里 N3 的 `test.fail` 用例要翻成普通断言，KNOWN-BUGS 登记同步更新。
- 深度校验（顺带解决 CONCERNS 里的 XSS 和畸形数据）：日期必须 `YYYY-MM-DD`，id 必须过 id 正则，`cat` 必须是已知类别（旧类别名走 `LEGACY` 映射），力量值必须是数字，文件大小设上限（如 5 MB）。校验失败则整个文件拒绝，而不是部分导入。

#### 5.2 导入计划还是记录

| 文件类型 | 导入后的效果 |
|----------|--------------|
| 旧备份（无计划） | 只替换记录，**当前计划保持不动** |
| 新备份（含计划和记录） | 两者都替换。确认框里写明会替换哪些 |
| 仅计划的文件（车主种子） | 只替换计划，记录不动 |

确认框要给**摘要**而不是一句“确定吗”：“备份包含 N 条记录（日期范围）、M 个目标组、K 个任务；将替换当前账号的……；当前账号现有 X 条记录”。

#### 5.3 安全措施

| 措施 | 优先级 | 说明 |
|------|--------|------|
| 拒绝非备份文件、确认前不写入任何东西 | P1 | 见 5.1 |
| 摘要确认框 | P1 | 沿用原生 `confirm()` 或换成 `<dialog>`，由实现阶段决定；测试里已有 `confirm` 的处理方式 |
| 导入前自动留一份当前状态，提供“撤销导入” | P2 | 5 秒的 toast 不够，建议保留到下次刷新或一段较长时间，存本机即可 |
| 取消后能用同一个文件重试（B2） | P2 | 取消时也清空 `input.value`；一并修，改动极小，需要翻转 B2 的 `test.fail` |
| 按账号作用域 | P1 | 导入只写当前登录账号，不能写别人 |
| 合并式导入（只加不覆盖） | 不做 | 反特性 |

#### 5.4 导出

- 导出按钮不再依赖 `downloads` 能力，改用 `Blob` 加 `<a download>`，所有环境都显示。现有 `window.__dl` 旁路可以删除。
- JSON 导出输出新格式；CSV 导出保留，数据来源改成“计划 + 记录”。文件名可含日期，不含个人信息。
- iOS 主屏幕应用里 `<a download>` 会走系统的预览/分享流程，可用但体验一般（MEDIUM）。必要时补 Web Share API，作为后续优化。

#### 5.5 从旧托管副本迁移（车主操作，推荐顺序）

1. 车主自己在旧的托管应用里点“备份 JSON”（我们不访问、不修改旧应用，也不读取这份文件）。
2. 在新站用车主账号登录。此时账号里是示例计划。
3. 导入**车主种子计划**（本地脚本生成，不进 git），用 `P<n>` / `P<n>-<i>` 原 id，所以旧进度可以直接对上。
4. 导入第 1 步下载的旧备份（只含记录），看摘要里的“找不到对应计划项”提示应为 0，确认。
5. 对照计数核对（记录条数、目标组完成情况、力量历史），旧托管应用保持原样放一段时间作为后备。
6. 在导入全过程的演练中**只用合成数据**，在本机临时的 PocketBase 实例或测试模拟后端里先跑通一遍，真实数据只进真实服务器。

## Feature Dependencies

```
种子计划生成脚本 ──requires──> 计划移出代码、存到服务器
计划存服务器 ──requires──> 稳定 id 方案（冻结现有 id）
编辑计划页 ──requires──> 计划存服务器 + 空状态渲染 + 归档支持 (allTasks)
车主迁移 ──requires──> 计划导入 + 旧备份导入 + 修 N3（拒绝非备份）

登录页 ──requires──> 账号隔离（集合规则）
会话持久化 ──requires──> 登录页
实时订阅 ──requires──> 登录页（订阅要带认证）
离线优先 ──requires──> 本机缓存按用户 id 分 key ──requires──> 登录页（知道是谁）
离线优先 ──requires──> 修 flush（失败重试）+ 修加载前修改被覆盖

实时更新 ──requires──> 不毁草稿的渲染（保存并恢复 UI 状态）
实时订阅 ──requires──> 重连整份对账
状态栏状态机 ──enhances──> 离线优先 + 实时同步

应用壳离线（service worker）──enhances──> 离线优先（刷新后仍能打开）
示例计划 ──requires──> 计划存服务器（固定 id 保证幂等）

按 id 合并 logs ──enhances──> LWW（作为后续里程碑）
冲突前留底 ──enhances──> LWW
合并式导入 ──conflicts──> 导入即替换的简单模型
编辑计划草稿保存 ──conflicts──> 边输入边实时同步计划
```

### Dependency Notes

- **计划存服务器 requires 稳定 id：** 一旦计划可以编辑，位置 id 就会让进度错位。冻结现有 id 是零成本方案，必须在编辑页之前定下。
- **离线优先 requires 修 flush：** 现有 `flush` 在保存前清脏标记，没有重试。离线后第一次上传失败就永远不再上传。
- **实时更新 requires 不毁草稿的渲染：** 现有完整重渲染会清掉草稿和焦点。本地操作时已经是已知问题，远端推送会让它频繁出现。
- **车主迁移 requires 先导计划再导记录：** 反过来导入时进度对不上，会出现大量“找不到对应计划项”的提示。
- **编辑计划页草稿保存 conflicts 实时计划同步：** 如果边输入边同步，别的设备会看到编辑到一半的计划，id 和顺序都会抖动。

## Competitor / Pattern Analysis

这个场景没有直接竞品；参照的是同类模式：

| 能力 | 常见做法 | 本项目采用 |
|------|----------|------------|
| 登录 | 邮箱加密码，浏览器保存令牌，启动时刷新 | 账号加密码，PocketBase `authStore` 加 `authRefresh` |
| 离线优先 | 本机优先存储，联网后同步；复杂的用 CRDT | 整份快照加脏标记，LWW，不上 CRDT |
| 实时 | WebSocket 或 SSE 推变更 | PocketBase SSE，重连后整份重拉 |
| 重置密码 | 邮件链接 | 管理员后台手动重置 |
| 备份 | 带版本号的 JSON 包装 | 新格式包装加兼容旧裸 state |

## Sources

- PocketBase 官方文档，认证：<https://pocketbase.io/docs/authentication/> —— `authRefresh` 返回新 token 加最新用户数据、不会让旧 token 失效；token 不存服务端，客户端持有；改超级用户密码会让其 token 失效。文档页**没有写**默认有效期和 localStorage 持久化（HIGH：页面内容；持久化和默认有效期 MEDIUM，需在实现阶段核对 SDK 文档）。
- PocketBase 官方文档，实时：<https://pocketbase.io/docs/api-realtime/> —— SSE 加订阅两步；创建、更新、删除事件；订阅按 ListRule/ViewRule 过滤；5 分钟无消息服务端断开、客户端自动重连；**未说明断线期间的事件是否补发**（HIGH）。
- iOS 存储回收资料：<https://www.itnews.com.au/news/apple-cops-flak-for-deleting-local-browser-storage-after-7-days-539833>、<https://developer.apple.com/forums/thread/710157>、<https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide> —— Safari 对站点 7 天无交互清理脚本可写存储；主屏幕应用单独计时。来源较旧、苹果文档很少，**当前 iOS 版本的行为未核实**（LOW–MEDIUM）。
- 项目内部：`.planning/PROJECT.md`、`.planning/codebase/ARCHITECTURE.md`、`INTEGRATIONS.md`、`CONCERNS.md`，以及对 app 文件结构的只读查看（`normalize`、`flush`、`init`、导入导出代码；未复制任何个人计划文字）。
- 速率限制、token 默认有效期、`authStore` 持久化键、iOS `<a download>` 行为：来自一般经验，**未在本次研究中逐条核实**（LOW–MEDIUM），列入实现阶段的核对清单。
